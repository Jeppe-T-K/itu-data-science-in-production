Exercise 1: MLflow Catch-Up

MLflow should be familiar to you at this point, so this first exercise is a quick catch-up to make sure everyone has a working setup and the core concepts (experiments, runs, parameters, metrics, artifacts, the model registry) are fresh. If you have never used MLflow before, don't panic - the exercise is a self-contained introduction, and everything you need is under the MLflow tracking quickstart.

MLflow has a lot of built-in "flavours" that make it easy to track models from well-known ML libraries such as scikit-learn or Tensorflow. That is what we use here - the custom models come in the next exercise.

Make sure MLflow and friends are installed (see Exercise 0 on the exercise intro page): pip install mlflow pip install scipy pip install scikit-learn

Exercise 1.1: Run an ML experiment

  1. Edit the resources/example_model.py script to log the model run with MLflow First import mlflow

    Then set the MLflow experiment via mlflow.set_experiment("My experiment name")

    Then start an MLflow run, log the parameters and the metric, and log the model as an artifact of the run:

    with mlflow.start_run() as run:
    mlflow.log_params(params)
    mlflow.log_metric("mean_squared_error", mse)
    mlflow.sklearn.log_model(lr, name="lasso_model")

    Finally, register the model in the model registry, pointing at the artifact you just logged. This two-step flow (log to the run, then register from the run) is exactly how the course project's training notebook does it:

    mlflow.register_model(
    f"runs:/{run.info.run_id}/lasso_model",
    name="lasso_regression_model",
)
  2. Run training with different parameters For example set alpha in params to 0.5.
  3. Compare the runs and select the best model You can compare the two runs via the printed output or via the MLflow UI:

    In the terminal run mlflow ui

    You can also select the best run programmatically, which is what the project's deployment notebook does when it picks the model to promote (there it orders by the test F1-score):

    runs = mlflow.search_runs(
    experiment_names=["My experiment name"],
    order_by=["metrics.mean_squared_error ASC"],
)
best_run = runs.iloc[0]

    Why is selecting "the best run" a decision you should make in code rather than by eyeballing the UI?
  4. What exactly is logged for each run? Check the mlruns directory or through the UI under "artifacts". For each run you should be able to find: the parameters you logged, the metric, and the model artifact together with its metadata (conda environment, the model's input signature if MLflow could infer one, ...).

    By default everything is stored locally under ./mlruns. MLflow can also log to a central place with mlflow.set_tracking_uri(...) - a database, or a tracking server your whole team shares. The course project, for instance, points MLflow at a local SQLite database so the run history lives in one file.

  5. Try to use autologging Add mlflow.autolog() and remove other MLflow logging
    Look at what the autologged run contains compared to your explicit logging. Which approach gives you more control? Why might a production training job (like the project's) prefer explicit logging of exactly the parameters and metrics it cares about?

If all of that went smoothly: great, you are caught up. The interesting part starts in the next exercise, where a model is more than what a standard flavour can express.
