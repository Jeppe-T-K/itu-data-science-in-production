Exercise 3: Serving the Model

Your model now sits in the MLflow registry, threshold and all - but it isn't serving anyone yet. The last step from "model" to "product" is putting it behind an API, so other systems (or humans) can get predictions on demand.

There are two ways to do that, and you will try both:

  1. Serve the model directly with MLflow. mlflow models serve starts a scoring server for any logged model, /invocations endpoint included. This is exactly how the course project serves its vial-classification model.
  2. Define the API yourself with FastAPI. When you need control over the contract - validation, documentation, response bodies - you write the service yourself. The go-to Python framework for that is FastAPI: it validates requests with pydantic, generates interactive documentation automatically, and is easy to test. The course project uses both together: a thin FastAPI app in front of the MLflow scoring server.

Exercise 3.1: Serve the model directly with MLflow

  1. Start the scoring server
    mlflow models serve -m models:/thresholded_logistic_model/1 -p 5001 --no-conda

    Under the hood this launches a FastAPI application run by uvicorn - the same stack you will use yourself in a moment. The -m flag accepts any model URI: a registry version like here, or a runs:/... URI.

  2. Call the invocations endpoint
    curl -X POST http://localhost:5001/invocations \
  -H "Content-Type: application/json" \
  -d '{"instances": [[12.0, 34.0], [95.0, 60.0]]}'

    The scoring server converts the JSON into a DataFrame and passes it to your wrapper's predict. The response is your wrapper's output, wrapped by the scoring server in a predictions key:

    {"predictions": {"predictions": [0, 1], "timestamp": "2026-10-30T09:41:12.842017+00:00"}}

    The course project calls the same endpoint the same way - only with base64-encoded images in instances instead of feature rows - and lives with the same wrapping rather than writing its own scoring server.

    Where did the threshold come from in these predictions? What happens if you send the wrong field name, or a string instead of a number?
  3. Check the health endpoint
    curl -i http://localhost:5001/health
    Is the response valid JSON? This bare-newline answer is exactly why the course project puts its own FastAPI app in front of the scoring server: to control what the endpoints actually respond. Keep that motivation in mind for the next part.

Exercise 3.2 (advanced): Define your own API with FastAPI

  1. Install and run a hello-world app pip install fastapi uvicorn

    Create app.py:

    from fastapi import FastAPI

app = FastAPI(title="Model service")

@app.get("/health")
def health():
    return {"status": "ok"}

    Run it with uvicorn app:app --reload and open http://localhost:8000/health - then http://localhost:8000/docs.

    What is the /docs page? (hint: OpenAPI). Why does every serious service have a health endpoint - remember the logging/monitoring part of the lecture?
  2. Load the model once at startup Use a lifespan handler to load your registered wrapper once when the app starts:
    from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.model = mlflow.pyfunc.load_model(
        os.environ.get("MODEL_URI", "models:/thresholded_logistic_model/1")
    )
    yield

app = FastAPI(lifespan=lifespan)

    Why load at startup instead of inside the endpoint? What would that do to latency? And why read the model URI from an environment variable?
  3. Add the invocations endpoint Define pydantic models for the request and response, so FastAPI both validates and documents the contract. The response mirrors the wrapper's output: predictions plus a timestamp.
    from pydantic import BaseModel

class Invocation(BaseModel):
    features: list[list[float]]

class Prediction(BaseModel):
    predictions: list[int]
    timestamp: str

@app.post("/invocations")
def invocations(payload: Invocation) -> Prediction:
    df = pd.DataFrame(payload.features)
    return Prediction(**app.state.model.predict(df))

    Start the service and try it:

    curl -X POST http://localhost:8000/invocations \
  -H "Content-Type: application/json" \
  -d '{"features": [[12.0, 34.0], [95.0, 60.0]]}'
    Compare the response to the one from the scoring server in 3.1: here it is not double-wrapped - defining the API yourself means controlling the contract. What happens if you send a string instead of a number? Or the wrong field name? Watch what FastAPI does for you - and discuss why "sanity check input/output" from the lecture matters.
  4. Make the health check complete A health endpoint that just returns {"status": "ok"} only tells you the process is alive - not that it can actually serve. Make it report on the model as well: return 503 with a "loading" status until the model is loaded, and only then 200 with "ok".

    The course project takes this further: its health check distinguishes ok / loading / error, because the model there runs in a separate process that can die independently of the API.

    Why does a load balancer (or an orchestrator like Docker/Kubernetes) care about the difference between "process alive" and "model ready"?

Exercise 3.3: Test the service

  1. Write an API test FastAPI ships with a test client, so you can test the service without running a server:
    from fastapi.testclient import TestClient

def test_health():
    response = TestClient(app).get("/health")
    assert response.status_code == 200
    assert response.json() == {"status": "ok"}

    Add tests for /invocations too (e.g. known input → expected class).

  2. Discuss: wire it into CI 
    You set up GitHub Actions in the previous lesson. What would a workflow step that runs these tests give you that the unit tests of the model alone do not?
