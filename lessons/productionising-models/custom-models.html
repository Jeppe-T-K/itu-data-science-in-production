Exercise 2: A Custom Model Wrapper

Sometimes you can't use a standard scikit-learn (or otherwise supported) model, so you have to define your own.

A very common case: a classification threshold. LogisticRegression.predict() classifies by picking the class with the highest predicted probability - for two classes, that means class 1 whenever P(y = 1) comes out above 0.5 - but 0.5 is not sacred. If one class is much rarer than the other, or a false positive is much costlier than a false negative, the useful threshold might be 0.3, 0.7, or anywhere else.

The threshold is a decision you make with data during experimentation, and it belongs with the model when you promote it to production - not hardcoded in some serving script by whoever deploys it. So in this exercise you will wrap the logistic regression from your example_model.py of Exercise 1 in a custom MLflow model that also stores the threshold, using MLflow's PythonModel:

Exercise 2.1: Question the default threshold

You already have a trained classifier: example_model.py from Exercise 1, with its train/validation/test split. Now start editing that script instead of starting over.

  1. Warm-up: look at the probabilities Look at predict_proba for a few validation samples. What exactly does the model output?
    Hints:
    • predict_proba returns one row per sample and one column per class, in the order of lr.classes_. For our two classes that is P(y = 0) (malignant) and P(y = 1) (benign). Each row sums to 1, and for binary classification the interesting part is column 1, i.e. predict_proba(X)[:, 1].
    • predict does not compute anything new - it picks the class with the highest probability (an argmax over the columns). For two classes that is exactly "class 1 if P(y = 1) > 0.5, else class 0" - at exactly 0.5 the tie goes to class 0. So predict is predict_proba with a hardcoded 0.5 decision rule - that default is what we are about to question.
  2. Sweep thresholds Using the validation split, compute precision, recall and F1 for thresholds from e.g. 0.1 to 0.9 in steps of 0.05, based on predict_proba. Then check how the chosen threshold performs on the test set.
    A possible implementation:
    def sweep_thresholds(lr, X_val, y_val):
    proba = lr.predict_proba(X_val)[:, 1]
    threshold_sweep = {}
    for threshold in np.arange(0.1, 0.91, 0.05):
        preds = (proba >= threshold).astype(int)
        threshold_sweep[round(threshold, 2)] = {
            "f1": f1_score(y_val, preds),
            "precision": precision_score(y_val, preds, zero_division=0),
            "recall": recall_score(y_val, preds, zero_division=0),
        }
    best_threshold = max(threshold_sweep, key=lambda t: threshold_sweep[t]["f1"])
    return best_threshold, threshold_sweep

    Why do we sweep on the validation split rather than the test split?

    Hint:

    The test set is our stand-in for "unseen production data" - once we optimize against it, it stops being unseen. The course project tunes its threshold on the validation set in exactly this way, and additionally uses macro F1 because its classes are imbalanced.

  3. Log the sweep to MLflow Log the whole threshold sweep as an artifact and the chosen threshold as a parameter, together with the usual training run: parameters, metrics (validation and test), and the (un-wrapped) model.

    Building on the MLflow code from Exercise 1, that could look like:

    mlflow.set_experiment("My experiment name")
with mlflow.start_run() as run:
    best_threshold, threshold_sweep = sweep_thresholds(lr, X_val, y_val)

    mlflow.log_params(params)
    mlflow.log_param("threshold", best_threshold)
    mlflow.log_dict(threshold_sweep, "threshold_sweep.json")

    mlflow.log_metric("validation_f1_score", threshold_sweep[best_threshold]["f1"])
    test_preds = (lr.predict_proba(X_test)[:, 1] >= best_threshold).astype(int)
    mlflow.log_metric("test_f1_score", f1_score(y_test, test_preds))

    mlflow.sklearn.log_model(lr, name="logistic_regression_model")

Exercise 2.2: Wrap it in a PythonModel

  1. Define the wrapper class Subclass mlflow.pyfunc.PythonModel. The wrapper holds both the fitted model and the threshold, and returns the predictions together with the threshold that produced them - a small taste of how the course project's wrapper returns predictions plus extra outputs (there: confidences, and a log of every request):
    class ThresholdedLogisticRegression(PythonModel):
    def __init__(self, model, threshold=0.5):
        self.model = model
        self.threshold = threshold

    def predict(self, context, model_input):
        # MLflow injects `context` into every predict call of a pyfunc
        # model: read-only metadata about where and how the model is
        # being invoked, with the fields
        #   request_id           - ID of this inference request (e.g. when
        #                         called through the scoring server)
        #   is_evaluate          - True when the call comes from mlflow.evaluate
        #   dependencies_schemas - schemas of the model's dependencies
        #   model_id             - ID of the logged model being served
        #   endpoint_name        - name of the serving endpoint, when the
        #                         model is served behind one
        # We need none of it here - the threshold travels on the model
        # object - but the signature has to accept it.
        if isinstance(model_input, pd.DataFrame):
            model_input = model_input.values
        proba = self.model.predict_proba(model_input)[:, 1]
        return {
            "predictions": (proba >= self.threshold).astype(int).tolist(),
            "threshold": self.threshold,
        }
  2. Log and register the wrapper Log the wrapper as the model artifact of the run with the pyfunc flavour:
    with mlflow.start_run() as run:
    ...
    mlflow.pyfunc.log_model(
        name="thresholded_logistic_model",
        python_model=ThresholdedLogisticRegression(lr, threshold=best_threshold),
    )

mlflow.register_model(
    f"runs:/{run.info.run_id}/thresholded_logistic_model",
    name="thresholded_logistic_model",
)

    Note that python_model is an instance - everything you store on it is serialized with the model. This is the same log-then-register flow you used in Exercise 1 and that the course project uses.

  3. Load it back and verify Load the model from the registry (mlflow.pyfunc.load_model("models:/thresholded_logistic_model/1")) and predict on the test set.

    Hardcoding the version number is fine for this exercise. You can avoid the hardcoding by referring to registry stages and aliases instead (e.g. models:/thresholded_logistic_model@production).

    Verify that the loaded model's predictions equal what you get by manually thresholding predict_proba at your chosen threshold. What happens if you load the scikit-learn flavour instead - does it know anything about your threshold?

  4. Experiment with the threshold Log a couple of runs with different thresholds (and the same underlying model). Look at the runs in the MLflow UI.

    You just ran several "experiments" that share the same trained model but represent different products. Why does it make sense to track the threshold as a first-class parameter of a run?
