Exercise 2: A Custom Model Wrapper

Sometimes you can't use a standard scikit-learn (or otherwise supported) model, so you have to define your own.

A very common case: a classification threshold. LogisticRegression.predict() classifies based on whether the predicted probability is above 0.5 - but 0.5 is not sacred. If one class is much rarer than the other, or a false positive is much costlier than a false negative, the useful threshold might be 0.3, 0.7, or anywhere else.

The threshold is a decision you make with data during experimentation, and it belongs with the model when you promote it to production - not hardcoded in some serving script by whoever deploys it. So in this exercise you will wrap a logistic regression in a custom MLflow model that also stores the threshold, using MLflow's PythonModel:

Exercise 2.1: Train a classifier (and question the default threshold)

  1. Generate classification data Use get_classification_data() from resources/data_util.py and train a LogisticRegression on the training split.

    The function returns a stratified 70/15/15 train/validation/test split - the same proportions the course project's training notebook uses for its vial images. The three sets have distinct roles:

    • train: fit the model
    • validation: make decisions during experimentation (like picking a threshold)
    • test: a final, untouched evaluation
    Look at predict_proba for a few test samples: what exactly does the model output? How does predict turn those probabilities into classes?
  2. Sweep thresholds Using the validation split, compute precision, recall and F1 for thresholds from e.g. 0.1 to 0.9 in steps of 0.05, based on predict_proba. Then check how the chosen threshold performs on the test set.
    Pick a "best" threshold for your metric of choice. Why is F1 at threshold 0.5 not necessarily the best choice? When would you favor precision over recall (or vice versa)?
    Why do we sweep on the validation split rather than the test split? (Hint: the test set is our stand-in for "unseen production data" - once we optimize against it, it stops being unseen.) The course project tunes its threshold on the validation set in exactly this way, and additionally uses macro F1 because its classes are imbalanced.
  3. Log the sweep to MLflow Log the whole sweep as an artifact (e.g. mlflow.log_dict(sweep, "threshold_sweep.json")) and the chosen threshold as a parameter, together with the usual training run: parameters, metrics (validation and test), and the (un-wrapped) model.

Exercise 2.2: Wrap it in a PythonModel

  1. Define the wrapper class Subclass mlflow.pyfunc.PythonModel. The wrapper holds both the fitted model and the threshold, and returns the predictions together with a timestamp of the prediction call - a small taste of how the course project's wrapper returns predictions plus extra outputs (there: confidences, and a log of every request):
    from datetime import datetime, timezone

class ThresholdedLogisticRegression(PythonModel):
    def __init__(self, model, threshold=0.5):
        self.model = model
        self.threshold = threshold

    def predict(self, context, model_input):
        if isinstance(model_input, pd.DataFrame):
            model_input = model_input.values
        proba = self.model.predict_proba(model_input)[:, 1]
        return {
            "predictions": (proba >= self.threshold).astype(int).tolist(),
            "timestamp": datetime.now(timezone.utc).isoformat(),
        }

    Why must the threshold live in the model object (or an artifact) instead of in the caller's code? And why does the wrapper return plain Python lists instead of numpy arrays? (Hint: the output has to survive being sent over HTTP as JSON.)
  2. Log and register the wrapper Log the wrapper as the model artifact of the run with the pyfunc flavour:
    with mlflow.start_run() as run:
    ...
    mlflow.pyfunc.log_model(
        name="thresholded_logistic_model",
        python_model=ThresholdedLogisticRegression(lr, threshold=best_threshold),
    )

mlflow.register_model(
    f"runs:/{run.info.run_id}/thresholded_logistic_model",
    name="thresholded_logistic_model",
)

    Note that python_model is an instance - everything you store on it is serialized with the model. This is the same log-then-register flow you used in Exercise 1 and that the course project uses.

  3. Load it back and verify Load the model from the registry (mlflow.pyfunc.load_model("models:/thresholded_logistic_model/1")) and predict on the test set.

    Hardcoding the version number is fine for this exercise. The course project avoids the hardcoding by referring to registry stages and aliases instead (e.g. models:/cnn_model@Production) - you will meet those ideas later in the course.

    Verify that the loaded model's predictions equal what you get by manually thresholding predict_proba at your chosen threshold. What happens if you load the scikit-learn flavour instead - does it know anything about your threshold?
  4. Experiment with the threshold Log a couple of runs with different thresholds (and the same underlying model). Look at the runs in the MLflow UI.
    You just ran several "experiments" that share the same trained model but represent different products. Why does it make sense to track the threshold as a first-class parameter of a run?
