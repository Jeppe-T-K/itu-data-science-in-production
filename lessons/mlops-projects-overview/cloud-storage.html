Exercise 5 (extra): Data and Models in S3-Compatible Object Storage

Your pipeline now runs locally, but everything it produces lives on your laptop. If a teammate (or a CI machine) clones your repo, data/raw/ and models/ are empty. Git is for code - data and model artifacts belong somewhere else.

In practice, that "somewhere else" is almost always an object store speaking the S3 API. The S3 protocol started as an AWS service, but is now the de-facto standard supported by everyone: DigitalOcean Spaces, Google Cloud Storage (S3-compatible API), Azure (via gateways), and self-hosted solutions like MinIO. Learning the S3 API once means you can talk to all of them.

In this exercise you will make your pipeline pull its raw data from and push its model artifact to an S3-compatible bucket, first locally with MinIO, then (optionally) against a real cloud provider.

Exercise 5.1: A local object store with MinIO

MinIO is an S3-compatible object store you can run locally - perfect for development, and it means you don't need cloud credentials to do this exercise. You already know the tool for the job from the containers lesson:

  1. Start MinIO in Docker 
    docker run -d --name minio \
  -p 9000:9000 -p 9001:9001 \
  -e MINIO_ROOT_USER=minioadmin \
  -e MINIO_ROOT_PASSWORD=minioadmin \
  minio/minio server /data --console-address ":9001"

    Open http://localhost:9001 and log in with minioadmin/minioadmin. The console looks different from AWS, but every button here has an S3-API equivalent.

  2. Create a bucket for your project Create a bucket, e.g. my-ds-project, either via the console or with mc.
    Given the data stages from the lecture, what "folders" (S3 uses key prefixes, not real folders) would you create inside the bucket?

Exercise 5.2: Talk S3 from Python with boto3

boto3 is the standard Python client for the S3 API - it works against AWS, Spaces, and MinIO alike, you just point it at a different endpoint_url.

  1. Install and configure credentials outside version control Add boto3 to your project dependencies. Then create a .env file (check that .gitignore ignores it - CCDS does this for you):
    AWS_ACCESS_KEY_ID=minioadmin
AWS_SECRET_ACCESS_KEY=minioadmin
S3_ENDPOINT_URL=http://localhost:9000
S3_BUCKET=my-ds-project
    Why must credentials never be committed? What could someone do with a leaked key to a real cloud bucket?
  2. Write a small storage helper In your package, add helpers for upload/download. The interesting part is that the client is configured from the environment, so the same code works against MinIO and a real cloud:
    import os
import boto3

def s3_client():
    return boto3.client(
        "s3",
        endpoint_url=os.environ["S3_ENDPOINT_URL"],
    )

    Try listing the objects in your bucket from Python (client.list_objects_v2) to verify the connection.

  3. Upload something Upload the raw data from Exercise 3 to s3://<bucket>/data/raw/... and verify you can see it in the MinIO console (or with mc).
    What happens if you upload the same key twice? What does that tell you about using the S3 key as your artifact "versioning"?

Exercise 5.3: Put the pipeline on storage

Now make the pipeline actually use the bucket:

  1. Ingestion pulls from S3 Change the data ingestion step to download the raw data from the bucket to data/raw/ if it isn't there already (rather than generating it locally). Local files are now a cache of the bucket, not the source of truth.
  2. Training publishes to S3 After training and evaluation, upload the serialized model and metrics.json to the bucket under a key that includes some notion of version or timestamp, e.g. models/<version>/model.pkl.
  3. Prove it is reproducible Delete data/ and models/ locally and re-run your pipeline (make pipeline or go run pipeline.go). Then simulate a fresh teammate: clone your repo into a new directory and run the pipeline there.
    What still breaks on a fresh clone that didn't break on your machine? (hint: where do the Python dependencies come from?)
